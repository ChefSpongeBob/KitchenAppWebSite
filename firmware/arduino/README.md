# Crimini temperature firmware

The firmware is two normal Arduino IDE sketches:

- `CriminiTempNode/CriminiTempNode.ino`: set `NODE_SERIAL` and the factory `RADIO_SECRET`, then upload it to each sensor.
- `CriminiTempGateway/CriminiTempGateway.ino`: set `GATEWAY_SERIAL`, the same `RADIO_SECRET`, and its separate factory-installed cloud credential, then upload it to the gateway.

Select **ESP32C6 Dev Module** for the TNY sensor nodes and **XIAO_ESP32C6** for the Seeed Studio XIAO gateway in Espressif's Arduino ESP32 package. Fit the gateway's 2.4 GHz external antenna before powering it; the gateway sketch selects the external connector using the XIAO RF switch (GPIO3 low, GPIO14 high). The node uses SDA GPIO18 and SCL GPIO19, reads temperature and humidity from the AHT20, transmits at 18 dBm in three short bursts with randomized spacing, and deep-sleeps for twenty minutes plus a small random delay. The bursts repeat one measurement, giving approximately three new readings per hour. The app uses a 25-minute node online window/default continuity gap; explicitly saved per-node settings remain unchanged. Pressure is not used. Use a distinct, unpredictable radio secret for each gateway kit (at least 16 characters); flash it into that gateway and only its nodes. Customers never enter this value. A short HMAC tag authenticates each radio reading; readings are not encrypted over the air. The node reserves sequence numbers in flash once per 256 readings so its counter survives battery changes. The gateway accepts both burst and acknowledgement-requesting frames during firmware rollouts, retains only the latest transient reading per node until upload, and the API rejects readings older than the node's last accepted sequence.

Use lowercase serials with letters, numbers, hyphens, or underscores, up to 31 characters. The node derives its radio address from that serial, so no separate node address needs to be configured. At the factory, put the gateway's assigned cloud credential in the gateway sketch, then provision the same serial and credential hash in D1:

```powershell
$env:CRIMINI_GATEWAY_CREDENTIAL="the-same-32-plus-character-value-flashed-into-the-gateway"
npm run ops:provision-temp-gateway -- --remote --serial=gateway-0001 --confirm=provision-temperature-gateway
Remove-Item Env:CRIMINI_GATEWAY_CREDENTIAL
```

Customers register the gateway serial in Crimini and choose **Wi-Fi Setup** under Registered Equipment. The guide works from a Wi-Fi-capable computer or phone. The gateway broadcasts `Crimini-` followed by up to the last 24 serial characters. Crimini displays its setup-network password to the authorized tenant manager; this is derived from the existing factory credential, not a new factory key. After joining that protected network, the customer opens the gateway's local setup page at `http://192.168.4.1/`, selects the restaurant's 2.4 GHz Wi-Fi, and enters its password. The page works without internet and does not load external assets. Wi-Fi credentials are tested in RAM and committed to gateway NVS only after a TLS-verified, authenticated Crimini check-in succeeds. Restaurant Wi-Fi details never pass through Crimini's server or D1. The customer then reconnects their computer/phone to normal Wi-Fi and checks the new gateway check-in in Registered Equipment. Only the wizard step and tenant/gateway IDs are retained in browser session storage; passwords are not retained there.

A gateway without stored credentials offers setup immediately. With an existing network, normal Wi-Fi reconnect and temperature reception continue first. After 10 minutes of failed Wi-Fi joins, the gateway temporarily pauses reception and reopens setup. It preserves the old credentials on failed setup; a 10-minute setup timeout restores normal receive/retry. The portal retries the old network when no setup client is attached. Successful setup closes the temporary network after Finish or 30 seconds, then resumes radio reception. This interval can miss sensor bursts and must be tested in the field. Cloud/API or clock failures alone do not trigger the Wi-Fi-failure fallback.

When no readings are waiting, the gateway makes a small authenticated cloud check-in every five minutes if no recent upload already confirmed connectivity. It creates no temperature rows. This keeps the registered gateway's status meaningful before nodes are added and detects Wi-Fi loss while sensors are quiet.

Then customers register each node serial under that gateway. The factory provisioning command does not generate credentials and sends only the SHA-256 hash to D1. Never commit either filled-in secret to the repository. A stolen radio secret allows forging readings for its kit until devices are reflashed; it does not grant cloud API access.

The gateway sketch uses `WiFi`, `WebServer`, and `DNSServer` included with Arduino ESP32 core 3.3.12. Keep `GatewaySetupPage.h` in the gateway sketch folder; Arduino IDE includes it automatically. No Bluetooth library is used. USB upload and serial-monitor settings are unchanged. Compile the sketch before choosing a partition scheme; no flash erase is part of setup.

Before shipping, test range, missed bursts, Wi-Fi/802.15.4 coexistence, outage recovery, and AA battery life on the actual boards. The gateway queue is RAM only, so a long outage or power loss can lose unsent readings. Do not erase a node's flash during updates: that resets its sequence and requires an intentional re-provisioning path. Factory firmware also needs a production plan for ESP32-C6 Secure Boot and flash encryption before secrets are placed on field devices.
